Temple TV: automatic offline broadcasts

Implementation and verification report · 16 October 2026 · requested Android release 1.0.76 / 146.

Not yet production-accepted. Software checks pass, but the new API has not been rolled out to production and installed-Android offline playback has not been verified. A production AAB build has been submitted to Expo; this report does not certify a finished or tested AAB.

Architecture inspected

  • The backend serves administrator-uploaded original MP4-family files from PostgreSQL-backed storage, including chunked objects and HTTP range delivery. HLS/transcoding is currently disabled.
  • The mobile app already had an Expo FileSystem download engine, durable queue metadata, integrity checking and an offline recording player.
  • The broadcast uses a server-directed two-buffer player. Live streams and YouTube content cannot be made genuinely offline through this mechanism.

Implemented changes

  • A paginated, short-lived cached backend manifest identifies eligible first-party uploaded recordings in the active broadcast lineup. Broadcast-specific grants reject unrelated/provider content.
  • Automatic preparation reuses the existing transfer queue; no new broadcast download button is required. It defaults to Wi-Fi/Ethernet, only runs in the foreground on broadcast surfaces, and pauses on cellular or navigation away from those surfaces.
  • One automatic transfer runs at a time. Other existing manual downloads keep their separate behavior. Duplicate video IDs share the same stored file.
  • Files are promoted from temporary storage only after length and SHA-256 verification. Legacy sources without a server checksum receive a persisted local digest; this does not independently prove publisher authenticity.
  • Durable broadcast copies persist across restarts and do not require a seven-day access renewal or a backend check to play locally. Existing manual-recording expiry policy remains separate.
  • The online broadcast player can reuse complete local copies on a subsequent bind. Speculative remote MP4 standby loading is suppressed on cellular/unknown transports without blocking actual playback handoff.
  • Offline broadcast mode selects a saved recording and progresses through locally available complete recordings without a server playlist request. Unverifiable files and decoder failures are skipped when another usable recording exists.
  • Automatic preparation reserves 256 MiB of free storage. Under pressure it may reclaim outdated automatic copies outside the current lineup, excluding pinned playback and copies originally downloaded manually. It does not guarantee that every catalog video fits on every device.
  • Thumbnails and completed media already held by the download engine are reused. Offline recording playback does not create a live viewer lease or pretend to be a live stream.

Data consumption: what is and is not established

  • Engine tests confirm that repeated local playback/validation does not start another media transfer or renew a durable broadcast grant.
  • Cellular is denied for automatic full-file preparation by default. An application configuration change is needed to permit it. Wi-Fi may itself be a metered hotspot; the transport check is not proof that the connection is unmetered.
  • The first preparation still transfers the original uploaded file's complete size. Source compression and new adaptive HLS renditions were not enabled on the memory-constrained API. Existing live/provider behavior is preserved.
  • No real-device before/after byte totals, battery measurements or slow-network throughput measurements were collected. No percentage saving is claimed.

Remaining release gates

  1. Finish and inspect the Expo native build, including its version, signing identity and release checks.
  2. Approve and deploy the manifest/grant API changes before expecting production clients to prepare recordings.
  3. Install the resulting release on representative supported Android devices. Verify complete preparation of real uploaded recordings over Wi-Fi; track actual bytes transferred.
  4. Enable airplane mode, stop the backend, force-close/reopen the app, and play multiple complete recordings through consecutive transitions. Verify seek/resume, audio, fullscreen and decoder compatibility.
  5. Repeat with slow/limited connectivity, Wi-Fi-to-cellular switching, background/foreground changes, interrupted transfers and low disk space. Confirm that manual downloads and active playback are never evicted.
  6. Confirm repeated playback generates no media network traffic, and that live streams/YouTube are never labelled as offline recordings.

Physical limits: no app can play a recording it has never received. Initial preparation needs connectivity, enough foreground preparation time and sufficient storage. App uninstall/data clearing removes private stored files. Original source codec compatibility and installed-device behavior remain validation requirements.
