# Coding Standards

Tooling (`ruff`, `black`, `mypy`, `pre-commit`) enforces syntax-level
consistency automatically — this document covers the conventions that
tooling can't check, because they're about *shape*, not syntax.

## Every response is an `Envelope`

Every endpoint returns `Envelope[YourSchema]` (success) or, on error, the
matching `ErrorEnvelope` — handled automatically by
`core/exception_handlers.py` for anything raised as `HTTPException` or
`RequestValidationError`. Never return a bare Pydantic model or dict
directly from an endpoint; never construct a JSON error response by hand
instead of raising `HTTPException(detail=ErrorDetail(...).model_dump())`.

## Endpoints don't touch SQLAlchemy

If an `api/v1/*.py` file has an `import` from `sqlalchemy` or references
`select(...)`, that's a sign the query belongs in a repository instead.
Endpoints call repository methods, build a response schema from the
result, and return it — that's the whole job. See
`docs/architecture.md`'s layering section for why this boundary is the
one that's enforced strictly here, even though the project doesn't have a
full separate domain-entity layer.

## Every fact-bearing table gets a `Verification` path

If you're adding a new entity type that represents a real-world fact
(a new government service category, a new kind of requirement) — not
every table needs this, but anything the API presents as "this is true
about the world" should be attachable to a `Verification` row. Add the
new entity to the `VerifiableEntityType` enum in
`db/models/geography.py` rather than inventing a parallel mechanism.

## No invented data, ever — seed scripts prove it

Every seed script (`scripts/seed_nigeria_business_registration.py` is the
reference example) must cite a real `Source` for every fact it inserts,
with a `Verification.confidence_score` that honestly reflects how sure
that source makes you. If a value isn't available from any source you
actually checked, leave the field `null` — don't estimate, don't guess a
"reasonable" number, and say so explicitly in the script's docstring (see
that script's handling of `typical_processing_time`, deliberately left
`None` with an explanation, versus the officially-sourced fee amounts).
This is a hard rule, not a style preference — it's the platform's entire
value proposition.

## Passive deletes on every one-to-many with a `NOT NULL` child FK

If you add a relationship where the child's foreign key column is
`nullable=False`, add `passive_deletes=True` to the parent-side
`relationship(...)` call *at the same time*, even if nothing deletes
through that path yet. See `docs/er-diagram.md`'s notes section and
Milestone 4's commit message for the bug this prevents — SQLAlchemy's
default delete handling tries to null out `NOT NULL` child columns in
Python before the parent's `DELETE`, which fails outright. This is cheap
to get right up front and expensive to debug later, since it only
surfaces the first time something actually deletes through that path.

## Async lazy-loading has no fallback

See `docs/developer-guide.md`'s dedicated section — worth restating here
as a hard rule: every relationship a response reads must be eagerly
loaded by the query that fetched the parent object. This has been the
most common real bug across every milestone's end-of-milestone review.

## `assert` is not error handling

Python strips `assert` statements entirely under `-O`. Never use `assert`
for anything that needs to hold in production — an invariant you believe
should always be true, input validation, permission checks. Use an
explicit `if ...: raise ...` instead. (`assert` is fine in test files,
where pytest's own assertion rewriting is the point.)

## Concurrent writes: don't trust a pre-check alone

"Does this email/slug already exist?" followed by an insert is a TOCTOU
race under concurrent requests. The pre-check is still worth doing (fast,
friendly error for the common case), but pair it with catching
`sqlalchemy.exc.IntegrityError` around the actual insert and translating
that to the same error response — the unique constraint is the real
guarantee, the pre-check is just a nicer error message for when you don't
need it.

## Commit boundaries live in one place

`db/session.py`'s `get_db_session` owns the commit-on-success/
rollback-on-exception boundary for every request. Repository methods
`flush()` (to get autogenerated IDs, to surface `IntegrityError` before
the endpoint's response is built) but never `commit()` — that's
deliberate, not an oversight. Adding a `commit()` inside a repository
method would commit a partial transaction if a *later* step in the same
request fails, defeating the whole point of the request-scoped
transaction boundary.

## Migrations are reviewed against models, not trusted from autogenerate

See `docs/developer-guide.md`. Every migration in this repo so far was
checked column-by-column, including `ondelete` behavior, against the
model it corresponds to.

## Docstrings explain *why*, not *what*

The codebase leans heavily on module/function docstrings and inline
comments that explain a *design decision* or a *bug that would otherwise
recur* — not restating what the next line of code obviously does. If
you're adding a comment, ask whether it would help someone who's about to
make the same mistake a past reviewer already caught, not whether it
describes the syntax below it.
